## Summary

This phase is primarily a frontend extension with minimal backend work. All target fields already exist in the `Empleado` model. The main backend gap is in `EmpleadoUpdateSerializer`: it exposes `entidad_bancaria` and `numero_cuenta_bancaria` but is missing `numero_cci`, `sistema_pensiones`, `tipo_comision`, `codigo_cuspp`, `genero_empleado`, `numero_ruc`, `provincia_domicilio`, and `departamento_domicilio`. The `mi_onboarding` endpoint returns an `OnboardingEmpleadoSerializer` that contains only checklist flags and no employee personal data — so the Personal tab must make a separate call or the page must fetch employee data independently.

The frontend currently has `OnboardingTabPersonal` with only 3 editable fields (telefono_celular, direccion_domicilio, fecha_nacimiento) and a hardcoded Zod schema. Extending this tab requires adding ~12 new fields, reorganizing into logical sub-sections, and implementing conditional AFP field visibility with `watch()`. The section-status panel can be computed purely from the `docs` array that is already fetched on the page — no new API endpoint is needed. `DocumentUploadZone` and `DocumentPreviewModal` already have the infrastructure to view existing docs (`archivoUrl` prop exists on the modal), but the upload zone's info card does not expose a "Ver documento" button yet.

The key architectural decision for ONBD-19/20/21 is the two-phase create-then-upload flow: the entity (familiar/academico/laboral) is POSTed first, then the document is uploaded with the newly returned ID. The "upload inside dialog" pattern means storing a `File` object in local state during the dialog, then uploading it in `onSuccess` of the entity mutation. This avoids any need for a temporary document API or staging endpoint.

**Primary recommendation:** Extend `EmpleadoUpdateSerializer` and expose the 8 missing fields; add a separate `GET /api/v1/rrhh/empleados/{id}/` call in `OnboardingEmployeePage` to populate Personal tab initial values; then extend the React form and add the status panel as a new component above the tab list.

### Pattern 4: Section Status Computation (client-side, no new endpoint)

**What:** Compute section status from the `docs` array already fetched on the page
**When to use:** ONBD-17

```typescript
// front/src/features/onboarding/components/OnboardingSectionStatus.tsx
type SectionStatus = 'completo' | 'en_revision' | 'observado' | 'pendiente'

const SECTION_DOC_TYPES = {
  personal: ['foto', 'dni', 'carnet_extranjeria'],
  familiar: ['dni_familiar', 'certificado_nacimiento', 'acta_matrimonio'],
  academico: ['certificado_estudios', 'titulo_profesional', 'certificado_capacitacion', 'diploma'],
  laboral: ['declaracion_jurada', 'cv', 'constancia_trabajo', 'carta_recomendacion', 'certificado_trabajo'],
}

function computeSectionStatus(docs: DocumentInfo[], sectionTypes: string[]): SectionStatus {
  const sectionDocs = docs.filter(d => sectionTypes.includes(d.tipo_documento))
  if (sectionDocs.length === 0) return 'pendiente'
  if (sectionDocs.some(d => d.estado_documento === 'rechazado')) return 'observado'
  if (sectionDocs.every(d => d.estado_documento === 'aprobado')) return 'completo'
  return 'en_revision'
}
```

**Confidence:** HIGH — logic follows the exact spec from CONTEXT.md and uses existing `docs` array. No backend changes needed.

### Pattern 6: Two-Phase Upload Inside Create Dialogs (ONBD-19/20/21)

**What:** File is staged locally in dialog state, then uploaded after entity creation succeeds
**When to use:** All three tab dialogs (familiar, academico, laboral)

Current state of dialogs:
- Familiar dialog: no upload field at all (upload happens post-creation in the card)
- Academico dialogs (cert, curso, titulo): no upload field at all (upload happens post-creation in the card)
- Laboral dialog: HAS an inline dropzone but uploads immediately on drop (no preview, no two-phase) — this is the worst pattern currently

Two-phase pattern for familiar/academico/laboral:

```typescript
// State additions to dialog component:
const [pendingDoc, setPendingDoc] = useState<{ file: File; tipo: string; label: string } | null>(null)
const [isPreviewOpen, setIsPreviewOpen] = useState(false)

// After entity mutation succeeds, upload doc if pending:
const createMutation = useMutation({
  mutationFn: createFamiliar,
  onSuccess: async (createdEntity) => {
    if (pendingDoc) {
      await subirDocumento(
        empleadoId,
        pendingDoc.tipo,
        'familiar',
        pendingDoc.label,
        pendingDoc.file,
      )
    }
    // invalidate queries, close dialog
  }
})
```

**Key insight:** The entity ID from the POST response (e.g., `familiar_id`) is not needed for the document upload — `subirDocumento()` uses `empleadoId` not `familiarId`. The doc is associated to the employee, not to the specific familiar record. This means the two-phase upload is just sequential: POST entity, then if `pendingDoc !== null`, POST document.

**For the preview:** Use a local `DocumentPreviewModal` instance in the dialog. File is selected → preview opens → user confirms → `setPendingDoc({ file, tipo, label })`, preview closes. When dialog "Guardar" is clicked, mutation runs; on success, if `pendingDoc`, upload it.

**Anti-pattern to avoid:** Do NOT trigger the actual upload from the preview confirm — that creates a timing problem where the entity might not exist yet. Stage the file in state; upload in mutation `onSuccess`.

### Anti-Patterns to Avoid

- **Uploading doc before entity creation:** Entity (familiar/curso) ID is not needed for doc upload (it uses `empleadoId`), but conceptually the entity should exist before the doc. Always POST entity first.
- **Mutating `EmpleadoUpdateSerializer` to be overly broad:** Only add the 8 missing writable fields, do not expose read-only computed properties (nombre_completo, edad, etc.).
- **Using `getValues()` for conditional rendering:** Only `watch()` triggers re-renders in react-hook-form.
- **Blocking dialog close during doc upload:** If the doc upload fails after entity creation, the entity is already saved. Show a toast error and allow the user to upload later via the card's upload zone.
- **Adding sistema_pensiones values not in model choices:** Values like "SIN PENSION" or "PENSIONISTAS" do not exist in `Empleado.SISTEMA_PENSIONES_CHOICES`. Use the actual model choices.

## Common Pitfalls

### Pitfall 1: sistema_pensiones Choices Mismatch
**What goes wrong:** CONTEXT.md lists "PENSIONISTAS" and "SIN PENSION" as choices, but the model defines `PENSIONISTA-SPP`, `PENSIONISTA-CMP`, `PENSIONISTA-OTRO` — no "SIN PENSION" at all.
**Why it happens:** CONTEXT.md was written before inspecting the model directly.
**How to avoid:** Use `Empleado.SISTEMA_PENSIONES_CHOICES` as the source of truth: `ONP`, `AFP PRIMA`, `AFP INTEGRA`, `AFP PROFUTURO`, `AFP HABITAT`, `PENSIONISTA-SPP`, `PENSIONISTA-CMP`, `PENSIONISTA-OTRO`. Confirm with user/planner whether "SIN PENSION" should be added to the model choices or is intentionally absent.
**Warning signs:** DRF validation error 400 when submitting "SIN PENSION" or "PENSIONISTAS" to the PATCH endpoint.

### Pitfall 2: OnboardingEmpleadoSerializer Does Not Return Employee Personal Fields
**What goes wrong:** `mi_onboarding` endpoint returns `OnboardingEmpleadoSerializer` which is a serializer of `OnboardingEmpleado` (the checklist model) not `Empleado`. Personal fields (genero, estado_civil, sistema_pensiones, etc.) are not in the response.
**Why it happens:** The serializer mirrors the onboarding checklist model, not the employee model.
**How to avoid:** Add a separate `useQuery` in `OnboardingEmployeePage` to `GET /api/v1/rrhh/empleados/{empleadoId}/` and pass the result as `initialValues` to `OnboardingTabPersonal`. Also update the read serializer (`EmpleadoSerializer` around line 480) to expose the missing fields.
**Warning signs:** Personal form shows blank values for all new fields even after data is saved.

### Pitfall 3: EmpleadoUpdateSerializer Missing Fields (PATCH Returns 200 But Ignores Values)
**What goes wrong:** PATCH succeeds silently but `numero_cci`, `sistema_pensiones`, etc. are not saved because they are not in `EmpleadoUpdateSerializer.Meta.fields`.
**Why it happens:** DRF silently ignores extra fields that are not in the serializer's `fields` list.
**How to avoid:** Explicitly add all 8 missing fields to the serializer. Test by reading back the saved values.
**Warning signs:** PATCH returns 200, no error, but GET of the employee still shows old values.

### Pitfall 4: Laboral Dialog Upload Pattern — No Preview
**What goes wrong:** Current `OnboardingTabLaboral` dialog has an inline dropzone that uploads immediately on drop, bypassing the preview-confirm flow required by ONBD-12 (already implemented elsewhere).
**Why it happens:** The laboral dialog was implemented differently from other upload zones — it uses its own dropzone, not `DocumentUploadZone`.
**How to avoid:** Replace the inline dropzone with the same two-phase pattern: stage the file in state, show `DocumentPreviewModal` for preview, then upload in mutation `onSuccess`. This brings laboral into alignment with all other upload zones.
**Warning signs:** User drops a file in the laboral dialog and it uploads immediately without preview — violates ONBD-12.

### Pitfall 5: "Ver Documento" on DocumentUploadZone with Missing archivo_url
**What goes wrong:** `existingDoc.archivo_url` may be `null` for some documents (if the file URL was not populated by the serializer).
**Why it happens:** `DocumentInfo` type declares `archivo_url?: string | null`.
**How to avoid:** Only show "Ver documento" button when `existingDoc.archivo_url` is truthy. When URL is null, either hide the button or show a disabled state with tooltip "Archivo no disponible".
**Warning signs:** iframe in modal renders blank / browser error for null URL.

### Pitfall 6: Dialog Re-mount Clears Staged File
**What goes wrong:** If the Dialog's `open` state is toggled while a `pendingDoc` is staged, the local state is reset (component unmounts).
**Why it happens:** Radix UI Dialog unmounts children when `open={false}`.
**How to avoid:** Reset `pendingDoc` explicitly in the dialog's cancel/close handler. Do not rely on unmount to clean up staged files — URL.revokeObjectURL must be called if a preview URL was created.
**Warning signs:** After closing and reopening the dialog, old file state bleeds over from memory.

   - What we know: The read serializer at ~line 480 includes `genero_empleado`, `estado_civil`, `distrito_domicilio`, `telefono_celular`, `entidad_bancaria`, `numero_cuenta_bancaria` but NOT `numero_cci`, `sistema_pensiones`, `tipo_comision`, `codigo_cuspp`, `numero_ruc`, `provincia_domicilio`, `departamento_domicilio`
   - What's unclear: Which specific serializer is used by `GET /api/v1/rrhh/empleados/{id}/` for the employee-facing request — `EmpleadoSerializer` or `EmpleadoDetailSerializer`?
   - Recommendation: Planner should add a task to inspect the EmpleadoViewSet.get_serializer_class() and update whichever serializer is used for the employee self-read endpoint.

3. **DocumentUploadZone empleadoId prop**
   - What we know: `DocumentUploadZone` accepts `empleadoId: number` in its props interface but the `handleUpload` function calls `uploadDocument()` / `uploadFoto()` which do NOT take `empleadoId` — they use the authenticated user's session on the backend
   - What's unclear: Is `empleadoId` actually used anywhere in the component? (Inspection says no — it is passed but unused)
   - Recommendation: When using `subirDocumento()` inside dialogs, the `empleadoId` is required. When using `DocumentUploadZone` standalone, it is handled server-side. No change needed to upload service.
