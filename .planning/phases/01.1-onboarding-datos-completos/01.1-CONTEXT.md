# Phase 1.1: Onboarding Datos Completos - Context

**Gathered:** 2026-03-15
**Status:** Ready for planning
**Source:** User requirements (conversation)

<domain>
## Phase Boundary

Esta fase completa el formulario de onboarding del empleado con todos los datos personales requeridos por RRHH, añade visibilidad de estado por sección, permite visualizar los documentos ya subidos, e integra la subida de documentos directamente dentro de los formularios de agregar dependientes/académicos/laborales.

Todos los campos objetivo ya existen en el modelo `Empleado` en la base de datos. El trabajo es principalmente frontend + serializer para exponer los campos faltantes. No se requieren nuevas migraciones de DB excepto posiblemente para campos que no existen aún.

</domain>

<decisions>
## Implementation Decisions

### Tab Personal — Campos adicionales (LOCKED — todos deben aparecer)

El tab Personal del onboarding debe incluir los siguientes campos que actualmente NO se muestran al empleado:

**Datos personales básicos:**
- Género (`genero_empleado`: choices masculino/femenino/otro)
- Estado civil (`estado_civil`: choices soltero/casado/conviviente/divorciado/viudo)
- RUC (`numero_ruc`: texto, opcional)

**Dirección de domicilio completa:**
- Dirección domicilio (`direccion_domicilio`) — ya existe pero se puede mejorar el layout
- Distrito (`distrito_domicilio`)
- Provincia (`provincia_domicilio`)
- Departamento (`departamento_domicilio`)

**Sistema de pensiones (LOCKED — lógica condicional):**
- Campo principal: `sistema_pensiones` con opciones (según modelo Django):
  - ONP
  - AFP PRIMA
  - AFP INTEGRA
  - AFP PROFUTURO
  - AFP HABITAT
  - PENSIONISTA-SPP
  - PENSIONISTA-CMP
  - PENSIONISTA-OTRO
  - SIN PENSION (NUEVO — agregar al modelo, no requiere migración de DB)
- Si se selecciona cualquier AFP (PRIMA, INTEGRA, PROFUTURO, HABITAT):
  - Mostrar campo CUSPP (`codigo_cuspp`) — Código de Identificación al SPP
  - Mostrar campo tipo de comisión (`tipo_comision`: flujo / mixta)
  - Mostrar campo celular (si no está ya en el form)
- Si se selecciona ONP, PENSIONISTAS o SIN PENSION: ocultar campos AFP

**Datos bancarios:**
- Entidad bancaria (`entidad_bancaria`)
- Número de cuenta bancaria (`numero_cuenta_bancaria`)
- CCI (`numero_cci`) — Código de Cuenta Interbancaria

### Panel de estado por sección (LOCKED)

Debe existir un componente visible al empleado que muestre el estado de cada sección:
- PERSONAL / FAMILIAR / ACADÉMICO / LABORAL
- Cada sección muestra: ✓ Completo / ⏳ En revisión / ⚠ Observado / ○ Pendiente
- "Completo" = tiene al menos un documento aprobado en esa sección
- "En revisión" = tiene documentos pendientes de revisión
- "Observado" = tiene al menos un documento rechazado
- "Pendiente" = no ha subido documentos aún

### Visualizar documentos subidos (LOCKED)

El empleado debe poder hacer clic en un documento ya subido para visualizarlo.
- La zona de upload (DocumentUploadZone) cuando muestra el badge de estado, debe tener un botón/link "Ver documento" que abre el modal de previsualización con la URL del documento existente
- No es necesario un visor PDF complejo — usar iframe con la URL del archivo ya almacenado

### Documentos integrados en formularios (LOCKED — aplica a los tres tipos)

**Familiares:**
- El dialog "Agregar dependiente" debe incluir campos de upload opcionales para el documento correspondiente según parentesco:
  - hijo/hija: DNI del familiar + Partida de nacimiento
  - cónyuge/conviviente: DNI del familiar + Acta de matrimonio / Certificado de unión de hecho
  - padre/madre: DNI del familiar + Partida de nacimiento
- El upload dentro del dialog es OPCIONAL — el empleado puede guardar el dependiente sin doc y subirlo después
- El flujo de upload dentro del dialog sigue el mismo patrón: preview modal → confirm → POST

**Académico:**
- Cada dialog de agregar (certificado de estudio, curso/diplomado, título profesional) debe incluir un campo de upload opcional para el documento certificador
- El usuario puede llenar el formulario escrito y subir el digital en el mismo paso, o dejarlo para después

**Laboral:**
- El dialog "Agregar experiencia laboral" debe incluir upload opcional para la constancia de trabajo
- Mismo patrón: opcional, preview antes de confirmar

### Claude's Discretion

- Organización visual del tab Personal (secciones/grupos de campos)
- Validaciones Zod para los nuevos campos (formato RUC, longitud CCI, etc.)
- Si los campos AFP/bancarios se separan en sub-secciones colapsables o se muestran directamente
- Orden de las sub-secciones dentro del panel de estado
- Si el backend necesita un nuevo endpoint para actualizar campos de pensiones/bancarios o si se reutiliza el PATCH a `/api/v1/rrhh/empleados/{id}/` con los campos adicionales
- Placement del panel de estado (encima de los tabs, dentro del progreso existente, o como tab adicional)

</decisions>

<specifics>
## Specific Ideas

**Campo sistema_pensiones ya existe en el modelo:**
```python
# back/app_rrhh/models/empleado.py
sistema_pensiones = models.CharField(...)  # AFP PRIMA, AFP INTEGRA, AFP PROFUTURO, AFP HABITAT, ONP, PENSIONISTAS, SIN PENSION
tipo_comision = models.CharField(...)  # flujo, mixta
codigo_cuspp = models.CharField(max_length=20, null=True, blank=True)
entidad_bancaria = models.CharField(max_length=100, blank=True, default='')
numero_cuenta_bancaria = models.CharField(max_length=30, blank=True, default='')
numero_cci = models.CharField(max_length=30, blank=True, default='')
genero_empleado = models.CharField(...)  # masculino, femenino, otro
estado_civil = models.CharField(...)
numero_ruc = models.CharField(...)
distrito_domicilio, provincia_domicilio, departamento_domicilio
```

**Serializer actual de onboarding:**
- `OnboardingEmpleadoSerializer` devuelve los datos del empleado para el frontend
- Necesita exponer los campos nuevos que el empleado puede editar
- El endpoint PATCH a `/api/v1/rrhh/empleados/{id}/` usa `EmpleadoUpdateSerializer` — verificar qué campos incluye actualmente

**Lógica condicional AFP en React:**
```tsx
const isAFP = ['AFP PRIMA', 'AFP INTEGRA', 'AFP PROFUTURO', 'AFP HABITAT'].includes(watch('sistema_pensiones'))
// Mostrar campos CUSPP y tipo_comision solo cuando isAFP === true
```

**Upload dentro de dialog — patrón sugerido:**
- Dentro del formulario del dialog, después de los campos de texto, un componente `DocumentUploadZone` en modo "inline" (sin altura fija, sin border-dashed grande)
- El archivo seleccionado se guarda en estado local hasta que el usuario confirma el formulario
- Al confirmar: primero POST el familiar/académico/laboral, luego POST el documento con el ID obtenido

</specifics>

- Validación de CUSPP formato exacto (8-12 dígitos) — implementar validación básica, formato exacto es Claude's discretion

</deferred>
