# D.1b — Drop Legacy Payroll + audit_lite.schema_version Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Drop the 9 legacy `apps.payroll` models + 2 services + seed command (now zero-consumer after D.1a), add the `AuditEvent.schema_version` field required by ADR-D.3, and define the canonical `payroll.*` audit action namespace — leaving `apps.payroll` as an empty, clean app ready for greenfield models in D.2.

**Architecture:** D.1a already decoupled every consumer (`grep "from apps.payroll"` under `apps/api/api/` = 0). D.1b deletes the model classes + service files + management command, then `makemigrations payroll` produces a `DeleteModel`-based migration (0003) that drops all 9 tables — migrations 0001/0002 are kept so the migration graph and test-DB build stay consistent (no squash; see Decisions). Separately, `audit_lite.AuditEvent` gains an `IntegerField schema_version` (default 1) via migration, and a new `apps/payroll/audit_actions.py` module declares the canonical event-name constants for D.5+.

**Tech Stack:** Django 5.2 + DRF, pytest. No frontend code changes (only a verification that App.tsx payroll page imports still resolve).

**Source:** `.planning/audit-D/BACKLOG.md` items #5, #6, #7, #8, #9, #10, #11, #12; ROADMAP-D Adjustment 1; ADR-D.3; INVENTORY § 1 + § 2.

## Decisions locked in this plan

1. **DeleteModel migration, not squash (deviation from BACKLOG #7):** BACKLOG #7 proposed squashing 0001+0002 into a clean initial. Instead D.1b keeps 0001/0002 and adds a `0003_drop_legacy_payroll` DeleteModel migration. Rationale: (a) safe — the migration graph and any cross-app dependency stay intact (Task 1 Step 1.2 confirms no external dep, but DeleteModel is robust either way); (b) CI-friendly — fresh and reused test DBs both build correctly (create→drop), whereas deleting migration files risks a `django_migrations` state mismatch on `--reuse-db`; (c) no manual DB ops on existing `bd_vyntia`. The "clean slate" intent of #7 is met: `apps.payroll` ends with zero models, and D.2 starts a fresh model line (0004+). The create-then-drop in test-DB build is harmless.
2. **App kept registered:** `PayrollConfig` + `settings/base.py` registration stay — D.2 adds models to the same app, so dropping the app would be churn.
3. **No frontend code change:** the 8 `features/payroll/pages/*` still exist and hit the D.1a 501 stub; they are rebuilt per phase (D.2/D.5/D.6). BACKLOG #11 is a tsc/build verification only.
4. **`audit_actions.py` placed in `apps/payroll/`:** even though payroll has no models yet, the constants belong to the payroll bounded context and are imported by D.5+ services.
